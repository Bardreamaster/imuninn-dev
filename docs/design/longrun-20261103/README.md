# 长时测试 2026-11-03：4 小时全流采集（插 USB，静置）

**条件**：iPhone 17 Pro，iOS 27，Release 包；USB 直连 Mac（供电 + 数据）；手机平放桌面不动、前台、不锁屏；`dataset` 预设（位姿 60 Hz、IMU 100 Hz、1920×1440@60 H.264 目标 12 Mbps、LiDAR 深度 60 Hz 平滑）；PC 端 `tools/bench/longrun.py` 每 10 s 记录一行，共 1440 行。

**结果**（`summary.json`、`longrun.png`）

| 项 | 结果 |
| --- | --- |
| 热状态 | 0–75 min nominal，75 min 起 **fair**，到 240 min 结束一直 fair，**未出现 serious / critical** |
| 帧率（PC 端 10 s 窗口均值） | 位姿 59.98 Hz、视频 59.98 fps、深度 59.98 Hz、IMU 99.8 Hz；最低一个窗口 54 Hz（见下） |
| 丢帧 | 视频累计 66 帧 / 86 万帧（0.008%），深度 / 位姿 / IMU 0；编码器丢帧 0 |
| 电量 | 100% 全程（充电中） |
| 视频码率 | 平均 0.45 Mbit/s |

**解读**

- 没有降帧：进入 fair 后手机端和 PC 端帧率都维持 60 Hz，iOS 的 fair 只是预警，没有限频。
- 视频丢帧集中在两处：77–87 min（刚进入 fair 的 10 分钟内丢了 50 帧，PC 端那几个窗口 57–59 fps）和 237 min（一个窗口丢 13 帧）。都是 TCP 发送端"只保留最新帧"策略在短暂拥塞时主动丢的，不是编码器丢，之后立即恢复。
- **码率只有 0.45 Mbit/s**：场景完全静止，H.264 几乎不出数据，所以编码器和网络的负载远低于实际使用（12 Mbit/s 目标）。这个测试反映的热负载主要来自相机 + ARKit 追踪 + LiDAR，**真实手持使用会更热**，需要再做一次有运动画面的测试。
- 插着 USB 既持续充电又挡住一面散热，和拔线走 Wi‑Fi 的情况不同。

**建议的后续测试**：① 同样 4 小时但画面有持续运动（对着屏幕播视频），看码率拉满时是否到 serious；② 拔线走 Wi‑Fi，看电池续航与热状态。
